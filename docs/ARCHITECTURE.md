# hwvault — アーキテクチャ・設計思想

このドキュメントは `hwvault` の設計思想・採用背景・脅威モデルを記述した開発者向けドキュメントです。
利用方法・APIリファレンスは [README.md](../README.md) / [README.ja.md](../README.ja.md) を参照してください。

---

## 1. プロジェクト目的

Go言語で開発するローカルCLI/デスクトップツール向けに、**開発者がセキュリティの詳細を意識しなくても、認証情報を特定マシンに安全にバインドして暗号化保管できる（Secure by Default）** ようにするライブラリ。

### 主なターゲット・ユースケース

- 非エンジニアを含む社内ユーザー向けローカルツールの認証情報保管
- チャットツールでの誤送信・Gitへの誤コミット・共有フォルダへの配置等による「他PCへのファイル流出・使い回し」の防止（ノードロック）

---

## 2. 採用背景と制約条件

| 検討した代替案 | 見送った理由 / 制約 |
|---|---|
| **AWS SDK / IAM直接参照** | 利用者が非エンジニアのローカル環境であり、個別のIAM権限を配布できないため |
| **リフレッシュトークン自動更新** | 接続先のAWSサービスの仕様上、リフレッシュトークンの自動更新が許可されていないため |
| **OS標準の資格情報ストア（`go-keyring`）** | ヘッドレスなLinuxサーバー環境等での動作検証・運用が困難なため |

## 3. 脅威モデルとセキュリティ設計方針

### ✅ 防ぐ脅威（In-Scope）

| 脅威 | 対策 |
|---|---|
| 暗号化ファイルの別PCへのコピー・流出による不正利用 | HW固有IDを鍵材料とするため、別マシンでは復号不可 |
| 不適切なファイルパーミッションによる同一PC内他ユーザーからの読み取り | `0600` / `0700` を強制適用 |
| 保存データの改ざん | AES-256-GCM の認証タグにより検知・復号失敗 |

### ❌ 受容するリスク（Out-of-Scope）

| 脅威 | 理由・補足 |
|---|---|
| **同一PC上で動作するマルウェア・悪意あるプロセスによる復号** | 同じHWで動作するプロセスは原理的に同じ鍵を生成できるため防御不可。EDR・アンチウイルス等のPC防衛（第1層）に委ねる。 |
| **物理的なメモリダンプ・コールドブート攻撃** | 本ライブラリのスコープ外。 |
| **`salt` の漏洩による鍵の推測** | `salt` 単体では鍵を生成できない（HW IDが必要）。ただし `salt` の管理はアプリ側の責任。 |
| **HW IDのスプーフィング（仮想マシン等での偽装）** | VM環境でのHW ID偽装には対応しない。VM利用時の挙動はアプリ側で考慮すること。 |

### 多層防御における位置づけ

```
第1層: EDR / アンチウイルス（マルウェア対策）
第2層: hwvault（ファイル流出時の不正利用防止）  ← ここ
第3層: アプリ側の認証・認可ロジック
```

## 4. 技術仕様・アーキテクチャ

### ハードウェアIDの取得（クロスプラットフォーム）

| OS | 取得元 |
|---|---|
| Linux | `/etc/machine-id` |
| Windows | `MachineGuid`（レジストリ） |

クロスプラットフォームなHW ID取得には [`machineid`](https://github.com/denisbrodbeck/machineid) パッケージを利用する。
このパッケージは各OSごとに単一の取得方法（Linux: `/etc/machine-id`、Windows: `MachineGuid`、macOS: `IOPlatformUUID`）を用いるため、独自のフォールバック処理（例: BIOS UUID直接取得）は現時点では実装しない。取得に失敗した場合は `ErrHWIDUnavailable` を返す。

#### コンテナ（Docker等）環境について

本ライブラリは主にオンプレミス・ベアメタルまたはVM環境での利用を想定して設計されており、コンテナ環境は現在のユースケースの対象外である。`machineid` パッケージが依拠する `/etc/machine-id`（Linux）は、コンテナランタイムやイメージによって存在しない場合や、コンテナインスタンス間で異なる場合、再作成時に変化する場合がある。コンテナ環境での挙動はhwvaultによって保証・検証されていない。

#### macOSの対応方針

`machineid` パッケージはmacOS（`IOPlatformUUID`）に対応しているため、理論上は動作するはずである。しかし、動作検証にはmacOS CI runnerが必要となり、現時点では維持コストが高いと判断し、実際の動作検証（CI含む）は行わない。「未検証」として扱う。



### 鍵生成（Key Derivation）

```
[HW ID] + [appSecretSalt]
        ↓
   HMAC-SHA256
        ↓
  [256bit AES鍵]
```

取得したHW情報とアプリ固有ソルト（`salt`）を HMAC-SHA256 でハッシュ化し、256bitのAES暗号鍵を動的に生成する。

`salt` / `plainText` の長さ・内容に関するhwvault独自の制約は設けない。利用する暗号ライブラリ（`crypto/hmac`, `crypto/aes` 等のGo標準パッケージ）の制約に従う。


### 暗号化方式

**AES-256-GCM** を採用。改ざん検知機能（認証タグ）付きの業界標準暗号化方式。

### 保存フォーマット

```
[ version(1byte) | nonce(12byte) | ciphertext+tag(...byte) ]
```

- `version` フィールドを先頭に置くことで、将来のアルゴリズム変更に対応可能
- `nonce` は `crypto/rand` で毎回生成（12バイト）

#### `version` フィールドの運用方針

`version` バイトは保存ファイルのフォーマット世代を表す値であり、ライブラリ自体のGoモジュールSemVer（`vX.Y.Z`）とは別軸の概念である。両者を以下のように対応付ける。

| ライブラリSemVerの変更 | 意味 | `version` バイトへの影響 |
|---|---|---|
| **メジャー**（例: v1→v2） | API互換なし（`Save`/`Load`のシグネチャ変更等） | 新フォーマットが導入される場合あり |
| **マイナー**（例: v1.1→v1.2） | API互換あり、既存vaultファイルの再生成が必要 | **インクリメント**（例: `0x01`→`0x02`） |
| **パッチ**（例: v1.1.0→v1.1.1） | バグ修正等、フォーマット非互換なし | 変更なし |

運用ルール:

- `Save` は常に現在サポートする最新の `version` を書き込む。
- `Load` は読み込んだ `version` が既知（サポート対象）であれば復号処理を行う。未知の `version`（将来のバージョン、または非サポートの旧世代）を検出した場合は `ErrUnsupportedVersion` を返す。
- 旧フォーマットの後方互換読み込みは**意図的にサポートしない**。「マイナーバージョンアップ＝既存vaultは再生成が必要」という設計思想を、Load側でも一貫させることで実装をシンプルに保つ。
- `ErrUnsupportedVersion` はアプリ側で `ErrDecryptionFailed` と同様に扱う（保存データ削除 → 再ログイン促進）。

### ファイル・パーミッション制御

- 保存先ディレクトリが存在しない場合はパーミッション `0700`（所有者のみアクセス可）で自動生成
- 保存ファイルはパーミッション `0600`（所有者のみ読み書き可）を強制（既存ファイル上書き時の対策として `os.Chmod` も適用）
- `Load` 実行時、既存ファイルのパーミッションが `0600` でない場合は**警告を出力する（エラーとはしない）**。バックアップからの復元や他ツールによる操作等、正当な利用ケースで復号自体を妨げないための方針。

### `filePath` の扱い（パス解決・相対パス）

- `hwvault` は `filePath` に対して `~` 展開等の独自パス解決を行わない。絶対パスの解決は呼び出し側の責任とする。
- 相対パスを渡した場合は、Go標準の `os` パッケージの挙動に従い、**カレントワーキングディレクトリ基準**で解決される（hwvault独自のパス基準は設けない）。


### アトミックな書き込み（`Save`）

`Save` は既存ファイルへの上書きを許可する。書き込み中のクラッシュやディスクフル等による**既存の有効なvaultファイルの破損・消失**を防ぐため、以下のアトミック書き込みパターンを採用する。

```go
// 1. 保存先と同じディレクトリに一時ファイルを作成する（同一ファイルシステムであることが重要）
tmpPath := filePath + ".tmp"
os.WriteFile(tmpPath, encryptedData, 0600)

// 2. os.Rename でアトミックに置き換える
os.Rename(tmpPath, filePath)
```

- `os.Rename` は同一ファイルシステム内であればOSレベルで不可分（アトミック）操作となるため、リネーム前にクラッシュしても元のファイルは無傷のまま残る。
- 一時ファイルは必ず保存先と同じディレクトリに作成すること（異なるファイルシステム間のリネームは失敗する）。
- 実装コストは小さい一方、認証情報という重要データの消失防止に対する効果が大きいため採用する。

### 並行処理について

本ライブラリはCLIツールでのログインフロー等、単一プロセスでの一時的な利用を想定しており、**複数プロセス・複数goroutineからの同一ファイルへの同時アクセスはサポートしない**。ファイルロック等の排他制御は実装しない。

## 5. APIインターフェース設計（2層構造）

暗号化のみを行いたいケースと、ファイル保存まで一括で行いたいケースの両方に対応できるハイブリッド設計。

```go
// 【高レベルAPI】ファイル操作・パーミッション管理・暗号復号を一括処理（メイン利用）
func Save(filePath string, plainText string, salt string) error
func Load(filePath string, salt string) (string, error)

// 【低レベルAPI】メモリ上での暗号化/復号のみ（標準暗号化ライブラリとしての利用）
func Encrypt(plainText string, salt string) ([]byte, error)
func Decrypt(cipherData []byte, salt string) (string, error)
```

## 6. エラーハンドリング・運用方針

### エラー定義

| エラー | 発生条件 |
|---|---|
| `ErrDecryptionFailed` | 別PCへのコピー、HW変更、ファイル破損 |
| `ErrHWIDUnavailable` | HW ID取得失敗（権限不足・非対応環境） |
| `ErrInvalidData` | 保存データのフォーマット不正 |
| `ErrUnsupportedVersion` | 保存データの `version` バイトが現バージョンのhwvaultで非対応（詳細は「4. 技術仕様・アーキテクチャ」の`version`フィールド運用方針を参照） |


### HW変更時のフォールバック方針

PCのパーツ交換やOSアップデート等でHW情報が変化し、復号エラー（`ErrDecryptionFailed`）が発生した場合は、アプリ側で「認証情報の初期化」とみなし、ユーザーへ再ログイン（パスワード再入力）を促すUIへ流す運用とする。

```
復号失敗 (ErrDecryptionFailed)
    ↓
古い vault ファイルを削除
    ↓
ユーザーに再ログイン（パスワード再入力）を促す
    ↓
新しいHW IDで再暗号化・保存
```

## 7. 類似ライブラリとの比較：`go-keyring`

[`go-keyring`](https://github.com/zalando/go-keyring) は、OS標準の資格情報マネージャー（macOS Keychain・Windows Credential Manager・Linux Secret Service）をバックエンドとして利用するライブラリ。

| 項目 | `hwvault` | `go-keyring` |
|---|---|---|
| **保管バックエンド** | HW固有IDで暗号化したファイル（任意のパス） | OS標準の資格情報マネージャー |
| **ノードロック（別PCでの復号防止）** | ✅ HW IDが異なれば復号不可 | ✅ OS資格情報ストアに紐付くため別PCでは取得不可 |
| **ヘッドレスLinux対応** | ✅ デーモン不要・ファイルのみで動作 | ❌ `gnome-keyring` 等のデーモンが必要なケースがある |
| **CI/CDパイプライン・サーバー環境** | ✅ 動作可能 | ⚠️ 環境依存（Secret Serviceが使えない場合がある） |
| **保管場所の可搬性** | ✅ ファイルパスを自由に指定可能（バックアップ・移行が容易） | ❌ OS管理のストアに保存されるため場所を制御しにくい |
| **macOS対応** | ⚠️ 未検証 | ✅ Keychain経由で安定動作 |
| **Windows対応** | ✅ 対応 | ✅ Credential Manager経由で対応 |
| **外部デーモン・サービス依存** | ❌ なし（依存ゼロ） | ⚠️ OS資格情報サービスへの依存あり |
| **暗号化の透明性** | ✅ 実装がコード上で完全に把握可能 | ❌ OSの実装に依存（ブラックボックス） |
| **ファイルパーミッション制御** | ✅ `0600` / `0700` を強制 | — （OS管理のため不要） |

`go-keyring` を見送った主な理由はヘッドレスなLinuxサーバー環境等での動作検証・運用が困難なためであり、本ライブラリではOS資格情報マネージャーへの依存を排除したファイルベースの暗号化方式を採用している。
